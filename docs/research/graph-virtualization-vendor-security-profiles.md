# Graph virtualization vendors: how they authenticate to sources and control access

> **Scope.** One profile per vendor that exposes non-graph data (warehouses,
> lakehouses, relational databases) as a graph without copying it, plus the
> adjacent categories the question raised: native graph-database federation and
> GraphQL federation. PuppyGraph gets its own document. Each profile answers the
> same five questions so the synthesis document can compare them side by side.
>
> **Method.** Facts come from vendor documentation read on 2026-09-09. Claims
> found only in search-engine snippets of a vendor page are marked
> `[snippet]`; claims found only in third-party coverage are marked
> `[secondary]`. "Not documented" means the vendor's public docs were checked
> and say nothing. Nothing is inferred from marketing copy.
>
> **The five questions per vendor**
> 1. Outbound: how does it authenticate to the source, and where do credentials live?
> 2. Identity: does the end user's identity reach the source (delegated), or does one service identity do all the work (trusted subsystem)?
> 3. Inbound: how do users authenticate to the product, and what authorization model does it enforce?
> 4. Schema: how does it discover source schema, and what source privileges does that need?
> 5. Operations: what does the vendor say about rotation, audit, and least privilege?

**Reading the table.** Only three products in this tier ever let the end user's
identity reach a source, and two of those (Neo4j, Neptune) only do so between
instances of themselves. Stardog is the single graph-virtualization product that
delegates to a warehouse, and even it introspects and creates virtual graphs with
the service account. Everyone else is a trusted subsystem that re-implements
authorization inside the virtualization layer.

## 1. Stardog

**Outbound.** A data source is a Java properties file: `jdbc.url`,
`jdbc.username`, `jdbc.password`, `jdbc.driver`, with `ext.*` keys passed straight
to the JDBC driver and Tomcat pool settings alongside. Registered with
`stardog-admin data-source add`. The docs say: "The configuration of a data source
requires the credentials for a Stardog system account that has access to the
backing database. By default, these credentials will be used for all interactions
with the database - creating virtual graphs, loading table metadata, and, in
particular, submitting virtual graph queries." Passwords are masked in option
listings. Encryption at rest for data-source credentials is not documented.
Source-specific notes: BigQuery uses a service-account JSON key and the docs list
the minimum IAM permissions (`bigquery.datasets.get`, `bigquery.jobs.create`,
`bigquery.readsessions.create`, `bigquery.tables.get`, `bigquery.tables.getData`,
`bigquery.tables.list`, `resourcemanager.projects.get`). Snowflake key-pair auth
is not documented; only username and password are shown.

**Identity.** Default is a single shared identity: "virtual graph queries for all
Stardog users are executed using these common, shared credentials", with
named-graph security as the per-user control. Pass-through is opt-in and
OAuth-only (`jdbc.passthrough=OAUTH`, `jdbc.passthrough.scope`), supported for
Databricks and Snowflake (Entra ID or Okta), Amazon Aurora (any OAuth IdP via
AWS STS web-identity federation plus IAM database auth), and REST via the CData
driver. Entra uses the Microsoft on-behalf-of flow; Okta uses RFC 8693 token
exchange configured in `jwt.yaml`. Per-source templates substitute the exchanged
token: `passthrough.token={ACCESS_TOKEN}` for Snowflake,
`passthrough.Auth_AccessToken={ACCESS_TOKEN}` for Databricks. Even in pass-through
mode the service account still performs virtual-graph creation and schema
introspection; only query execution runs as the user. Row-level and column
masking are expected to be implemented at the source.

**Inbound.** RBAC with permissions as (subject, action, resource). Actions are
read, write, create, delete, grant, revoke, execute, all. Resource types include
db, user, role, named-graph, virtual-graph, data-source, metadata, admin, and
sensitive-properties. Ships with an `admin/admin` superuser. Authentication via
internal bcrypt store, LDAP, or Kerberos; OIDC through `jwt.conf` with issuer,
username and roles claim mapping, Azure group mapping, and auto-created users.
Stardog Cloud SSO is OIDC only (Entra ID, Okta); SAML is not documented.
Virtual-graph security: creating a VG on a shared data source needs `CREATE
virtual-graph` plus `READ data-source`; with named-graph security on, a `SERVICE`
call on an unauthorized VG errors while `GRAPH`/`FROM` silently return empty.

**Schema.** On data-source add or refresh, "the metadata (catalogs, schemas,
tables, columns, data types, constraints, row-count estimates) are queried" and
cached in the system database, scoped by `sql.schemas` and `sql.catalogs`.
Mappings are SMS2 (native) or an R2RML subset. Designer reads table structure and
the user models manually. Required DB privileges are documented only for
BigQuery.

**Operations.** Audit and access logs are off by default; enabled with
`logging.audit.enabled` and rotation settings. Secret rotation guidance is not
documented.

## 2. Timbr.ai

**Outbound.** Snowflake connects through the Snowflake JDBC driver; the UI takes
hostname, username and password, or a full JDBC URL, plus a free-text
"Additional Parameters" field. Key-pair, OAuth, role and warehouse handling are
not documented. Platform secrets are environment variables (`DB_PASSWORD`,
`OAUTH_SECRET`, …) supplied via Docker or Kubernetes secrets. Encryption of
stored data-source credentials is not documented.

**Identity.** One stored service credential per data source. User impersonation
or token passthrough is **not documented anywhere** in Timbr's docs. This
contradicts the Gemini starter note, which credited Timbr with "user
impersonation & token passthrough". Treat that claim as unsupported.

**Inbound.** OIDC via Okta or Entra ID with group-to-role sync (`ALTER ROLE …
SYNC`, a 24-hour default sync interval, Graph API read permissions on users and
groups). SAML and LDAP are not documented. Authorization is SQL-style: `GRANT
[EDIT|QUERY|ACCESS] ON {ontology|datasource|user|role|domain} TO USER|ROLE`, with
`WITH GRANT OPTION`. Row and column security are policy objects attached to
properties, concepts, mappings or views (`GRANT POLICY`, `SYS_POLICIES`). These
are enforced in Timbr, not pushed to source RLS.

**Schema.** The Data Mapper lets a user pick data source, schema and table and
shows column metadata; concepts are modeled first and mapped second. No
automatic ontology-from-schema is documented. Required source privileges are
not documented.

**Operations.** Audit logging and rotation are not documented. A Snowflake
Native App variant is **not documented** on docs.timbr.ai or timbr.ai, despite
appearing in the starter note.

## 3. RelationalAI

**Outbound.** There is no outbound connection. RelationalAI is a Snowflake
Native App on Snowpark Container Services. Install needs `ACCOUNTADMIN` or
`ORGADMIN`. Privileges granted to the application at install, described as
non-revocable: `EXECUTE TASK`, `EXECUTE MANAGED TASK`, `CREATE WAREHOUSE` (it
creates `RELATIONAL_AI_ERP_WAREHOUSE`), `CREATE COMPUTE POOL`, `BIND SERVICE
ENDPOINT`. Optional: `IMPORTED PRIVILEGES ON SNOWFLAKE DB` for Cortex.

**Identity.** "All CDC operations and SQL queries execute under the
`RELATIONALAI` role, not individual user roles." Row access and masking policies
therefore evaluate against that role only; the docs state "RAI doesn't support
user-based policies at the row and column level." The starter note's claim that
it "inherits host warehouse security natively" is true only at the coarse
level: the app is a Snowflake principal, but per-user policies do not apply.

**Data access.** Data reaches the engine by CDC data streams
(`api.create_data_stream`), which require `SELECT` on the source object, change
tracking enabled, and the `cdc_admin` application role. Streams sync roughly
once a minute `[snippet]`. This is replication into the engine, not query-time
virtualization.

**Inbound.** Application roles (`app_admin`, `cdc_admin`, `eng_admin`,
`all_schema_all`) cannot be granted to users directly; they are granted to
Snowflake database roles, and the installer creates `rai_admin` and
`rai_developer` `[snippet]`.

**Operations.** The docs recommend least privilege and writing row and masking
policies against the `RELATIONALAI` role, using mapping tables keyed on the app
role to approximate per-user scoping.

## 4. Ontop and Ontotext GraphDB

**Ontop (open source, and CDF's own Postgres leg).** Properties file with
`jdbc.url`, `jdbc.user`, `jdbc.password`, `jdbc.driver`; CLI overrides; Docker
image accepts `ONTOP_DB_*` environment variables and their `_FILE` variants,
which the docs recommend "to avoid storing or exposing sensitive data such as DB
passwords". Single JDBC identity, no delegation, and the SPARQL endpoint has no
inbound authentication of its own. Schema is read from JDBC metadata;
`ontop extract-db-metadata` serializes it to JSON so a deployment can run in
offline metadata mode and add view constraints by hand. Required DB privileges
are not documented.

**GraphDB.** Embeds Ontop 5.5.0 for virtual repositories. The Workbench
generates the JDBC properties file; virtual repositories are read-only; per-user
credential delegation is explicitly not supported. Inbound: Basic, GDB token,
OpenID, X.509, Kerberos; local bcrypt user store or LDAP; roles `ROLE_ADMIN`,
`ROLE_REPO_MANAGER`, `ROLE_USER`, `READ_REPO_<r>`, `WRITE_REPO_<r>`. LDAP, OpenID
and Kerberos need a Standard or Enterprise license. Fine-grained access control
is ACL rules over subject, predicate, object and context; applicability to
virtual repositories is not documented. Audit is configured through
`graphdb.audit.*` properties.

## 5. Altair Graph Studio (formerly Cambridge Semantics Anzo)

Database data sources take title, user, password, server and database. The
Graph Data Interface for in-query virtualization takes `s:url`, `s:username`,
`s:password`, `s:driver`, `s:token`, and the documented best practice is to
reference a Query Context (`{{@db.<id>.url}}`) "so that the sensitive details
are abstracted from any requests". Query Contexts live in AnzoGraph or as JSON
on the leader; encryption is not documented. Release notes mention adding the
user's SSO token to an inline-view query context for differentiated permissions
against systems such as Elasticsearch `[snippet]`. Inbound SSO is Keycloak
OIDC plus SCIM; authorization is artifact ACLs with inheritance from data
source to schema and from graphmart to layers. Source privileges are not
documented.

## 6. Neo4j

**Is it virtualization?** Composite databases federate Neo4j databases only.
The product that reads a warehouse without copying, Neo4j Virtual Graph, is in
private preview: it runs in Aura, connects to Snowflake with "a dedicated,
read-only service account" using RSA key-pair auth, and the model is built
manually, from constraints, or by GenAI. "Snowflake RBAC and governance apply
unchanged" means the service user's grants bound what the engine sees.

**Outbound and identity for composite databases.** Remote aliases store
`USER … PASSWORD …`, AES-GCM-256 encrypted in the system database with a PKCS12
keystore. Two modes: `STORED NATIVE CREDENTIALS` (single remote user; the docs
warn local users may inherit elevated remote rights) and `OIDC CREDENTIAL
FORWARDING`, introduced in 2026.01, which forwards the user's bearer token to
the remote Neo4j. APOC `apoc.load.jdbc` takes credentials in the URL, a config
map, or an `apoc.conf` alias.

**Inbound.** OIDC with group-to-role mapping, LDAP, Kerberos. Property-based
access control grants `READ {prop}` under a single-property predicate, with a
documented fail-open caveat for `DENY`. Alias management is a DBMS privilege.

## 7. Amazon Neptune SPARQL `SERVICE`

Read-only federation between Neptune clusters (external endpoints need a
reverse proxy inside the VPC). "Neptune-1 calls Neptune-2 with the same
credentials it was called with": the caller's IAM identity is forwarded, both
clusters must honour it, same account and region, and a non-IAM caller cannot
federate to an IAM-enabled target. Inbound is SigV4 with actions such as
`neptune-db:ReadDataViaQuery` and a `QueryLanguage` condition key. No
graph-level row security. Audit logs record the caller ARN, auth context and
query payload.

## 8. TigerGraph

Not virtualization: data sources are for loading. `CREATE DATA_SOURCE` takes a
JSON block with Snowflake `connection.url/user/password` (key-pair via
`private_key_file` in the URL, with a dummy password still required), BigQuery
OAuth refresh token, S3 access keys or `InstanceProfileCredentialsProvider` or
session tokens, GCS service-account key, Azure shared key or service principal.
Kafka connector secrets can be externalised as `${file:…}`, `${env:…}`,
`${vault:…}`. Creating a data source needs `WRITE_DATASOURCE`. Inbound: built-in,
LDAP, SAML, OIDC, Kerberos, JWT; RBAC at global, graph, type and attribute
scope; row policies.

## 9. GraphQL federation, briefly

**Hasura DDN.** Snowflake via a JDBC URL held in an environment variable
(`valueFromEnv`), with "envelope encryption to secure all sensitive
information". `ddn connector introspect` generates models. Inbound JWT claims
become `x-hasura-*` session variables that drive `ModelPermissions` row filters
and `TypePermissions` column visibility. One service DB identity; row security
is Hasura-side. This is the cleanest published example of the "inbound claims
become row filters in the middle tier" pattern.

**Apollo GraphOS Router.** Inbound JWT via JWKS with rotation polling; the
docs recommend forwarding claims, not raw tokens, to subgraphs. Outbound
subgraph auth is AWS SigV4. Authorization directives (`@authenticated`,
`@requiresScopes`, `@policy`) are field-level; there is no row-level construct.

## 10. Corrections to the Gemini starter note

| Starter claim | What the docs say |
|---|---|
| Timbr: "user impersonation & token passthrough (delegates identity directly to Snowflake/Databricks)" | Not documented. Timbr stores one service credential and enforces row and column policies itself |
| Timbr: Snowflake Native App variant | Not documented on timbr.ai or docs.timbr.ai |
| RelationalAI: "inherits host warehouse security … natively" | Runs as the single `RELATIONALAI` role; per-user row and masking policies explicitly unsupported |
| Stardog: "JDBC service accounts or user credential delegation" | Correct, with the precision that delegation is OAuth-only, opt-in, and introspection still uses the service account |
| Stardog: "R2RML" mapping | Native format is SMS2; R2RML is supported as a subset |
| Neo4j Fabric as federation | Renamed composite databases; Neo4j-to-Neo4j only. Warehouse virtualization is a separate private-preview product |
